# 03 知识库与数据来源说明

## 1. 文档目的

本文档用于说明当前项目中 Dify / RAG 知识库、本地 FAQ、材料清单、口岸信息、养老服务信息等数据的用途、范围、来源边界、回答约束和后续维护建议。

本文档基于当前仓库中的 `dify-config/`、`files/`、`backend/`、`ElderCareApp/`、阶段总结文档和测试用例整理。当前仓库中无法确认来源链接或真实性的数据，统一标注为“待补充”或“当前仓库中未明确记录来源链接”。

## 2. 知识库用途

本项目当前使用三个 Dify 知识库，分别对应医疗就医导航、养老机构信息和政务办事问答。不同业务类型的问题通过后端路由选择对应知识库进行检索，避免跨领域知识误召回。

其中，政务办事知识库主要用于支撑港澳通行证、签注续签、过关材料、口岸服务等政策问答场景，使用户可以通过自然语言咨询办理问题，并由后端通过 Dify / RAG 返回结构化回答。

当前知识库与问答链路的作用包括：

- 支持用户自由提问，例如“G 签和 L 签有什么区别？”、“办理港澳通行证多少钱？”。
- 为 Android 前端提供结构化回答字段，包括标题、摘要、办理步骤、材料、注意事项、来源说明等。
- 为中老年用户提供更清晰、口语化的办理说明。
- 在政策不确定或知识库缺失时，提示用户咨询当地出入境窗口、口岸工作人员或官方渠道。

## 4. FAQ 与 RAG 的关系

FAQ 与 RAG 在当前项目中承担不同职责。

首页 FAQ 静态详情适合承载：

- 高频、稳定、简短的问题。
- 可本地秒开的固定答案。
- 用户无需个性化判断即可先了解的基础说明。
- 如“如何申请港澳通行证？”、“港澳通行证过期了怎么办？”、“老年人通关有哪些便利措施？”。

RAG 问答适合处理：

- 用户自由提问。
- 复杂情况判断。
- 多轮追问。
- 需要根据知识库召回材料进行组织回答的问题。
- FAQ 详情页无法覆盖的个性化问题。

当前仓库中已发现 FAQ 详情页实现：用户点击首页 FAQ 后进入本地 `FaqDetailScreen`，只有点击“继续追问”时才调用 `ChatViewModel.submitPrefilledQuestion()` 进入 RAG 问答。

这种分工可以减少等待时间和接口调用，避免高频固定问题每次都触发后端 Dify / RAG。

## 6. RAG 回答边界

RAG 回答应遵循以下边界：

- 回答应优先基于知识库内容，不应凭空编造政策。
- 对政策类、证件类、费用类、时限类问题，应提示以当地公安出入境管理部门、政府网站、官方政务服务平台或现场窗口最新要求为准。
- 当知识库没有明确依据时，不应强行给出确定结论，应说明“当前资料中没有找到明确说明”。
- 对不同地区、不同证件、不同用户身份、首次办理、换发、补发、签注类型等差异，应提醒用户进一步核实。
- 对费用、时限、有效期、停留时间等具体数字，只有知识库明确召回时才应写入回答。
- 对中老年用户，语言应简洁、礼貌、清楚，但不能过度简化政策风险。

当前 `policy_qa_prompt_structured_json.md` 已明确要求：

- 必须优先依据知识库内容回答。
- 不要编造政策。
- 知识库没有明确依据时需提醒咨询窗口或工作人员。
- 只输出合法 JSON。
- 涉及政策办理时一般需要人工核实提醒。

## 7. 知识库维护建议

### 如何新增资料

- 新增资料前先确认资料类型：正式政策资料、办事指南、FAQ、演示资料或测试资料。
- 优先收集官方政府网站、公安出入境部门、政务服务平台、口岸公告等来源。
- 将资料整理为清晰 Markdown 或可导入 Dify 的文档格式。
- 在资料顶部记录来源链接、采集日期、适用地区、维护人和版本号。

### 如何更新过期政策

- 为每份知识库文档维护 `版本号` 和 `更新时间`。
- 对费用、办理时限、签注停留时间、材料要求等高风险字段建立定期复核清单。
- 更新后同步修改 RAG 版本标记，例如 `RAG_KB_VERSION`。
- 更新后执行回归测试，尤其是费用、签注、材料、有效期等问题。

### 如何记录来源链接和更新时间

建议每条资料至少记录：

- 来源名称。
- 来源链接。
- 发布时间或页面更新时间。
- 本项目采集日期。
- 适用地区。
- 是否为官方来源。
- 是否已导入 Dify。

### 如何处理重复或冲突内容

- 同一政策存在多个来源时，优先使用更权威、更近期的官方来源。
- 对冲突内容不要合并成确定结论，应标注适用地区和更新时间。
- 对无法判断的冲突，写入人工核实提醒。
- 保留过期内容时，应明确标注“历史资料 / 不作为当前依据”。

### 如何区分正式政策资料和测试资料

- 正式政策资料应存放在明确的知识库目录，并记录来源。
- 测试资料和样例资料应标注“sample”或“test”。
- Dify 导入时应避免把测试用例、开发说明、阶段文档误导入正式知识库。
- RAG 回归测试应使用固定版本知识库，避免测试结果受临时资料影响。

## 8. 当前风险与限制

| 风险或限制 | 说明 |
| --- | --- |
| 政策时效性风险 | 证件、签注、费用、口岸规则可能变化，当前仓库未完整记录官方来源和更新时间。 |
| 来源不完整风险 | 多数本地资料未明确官方来源链接，后续上线前必须补充。 |
| Mock 数据与真实数据差异 | 口岸、材料清单、养老服务多为静态或 mock，不能代表实时真实情况。 |
| RAG 回答可能不稳定 | Dify 召回、Prompt、知识库版本和模型输出都可能影响结果。 |
| 语音识别影响准确性 | ASR 识别错误会导致后续问答问题偏离用户真实意图。 |
| 多语言一致性风险 | 部分显示文案已资源化，但仍有硬编码中文。 |
| FAQ 覆盖不足 | 部分 FAQ 只有问题文本，详情内容待补充。 |
| 外部服务依赖 | Dify、DashScope ASR/TTS、Qwen 等均需要可用 Key、网络和服务稳定性。 |

## 9. 当前状态总结

当前项目已具备 Dify / RAG 政策问答、结构化回答 Prompt、本地 FAQ、材料清单 mock、RAG 回归测试样例和若干资料文件。系统当前按医疗就医导航、养老机构信息、政务办事问答三个知识库分域组织资料，政务办事知识库在港澳通行证目标问题集上的召回效果较好。后续若用于正式项目或上线，应继续补齐政策来源、数据版本、更新流程，并为每个知识库维护独立评测题集，避免将 mock 数据、过期政策或跨领域资料误作为正式依据。
