# 04 后续优化计划

## 1. 文档目的

本文档用于基于当前仓库真实状态，整理项目后续可优化方向，并区分短期可完善内容、中期迭代内容、长期上线方向、上线前必须补充内容和公司级项目交付需要补充的材料。

本文档中的优化计划不代表当前已经完成，除非在当前仓库源码或文档中已有明确实现。

## 2. 当前项目状态概述

当前项目已经形成 Android 前端 + FastAPI 后端 + Dify/RAG 问答 + ASR 语音识别 + TTS 语音朗读 + 多语言展示 + 本地历史记录的基本闭环。

当前已具备的主要能力包括：

- Android Jetpack Compose 前端主界面和多页面状态切换。
- 首页服务入口、FAQ、本地口岸展示、材料清单入口。
- Chat 页文字提问、语音输入、结构化回答、朗读和历史记录。
- FastAPI 后端封装 Dify、RAG 缓存、ASR、TTS、材料静态接口。
- Dify / RAG 结构化 JSON Prompt 和港澳通行证知识库样例。
- FAQ 本地静态详情页。
- 朗读语言独立选择，展示语言跟随系统 Locale 的部分实现。
- 本地材料清单 mock 和本地办理判断规则。

当前仍需注意：

- 口岸信息、养老服务、材料清单等多处仍为静态或 mock。
- 部分服务入口为 Toast 占位。
- 政策资料来源链接和更新时间尚不完整。
- 真实上线所需的隐私、安全、账号、监控、运维等内容尚未补齐。

## 4. 中期优化计划

中期优化偏向项目继续迭代，重点提升用户体验、知识库质量和功能闭环。

| 优化事项                         | 目标                                                                       |
| -------------------------------- | -------------------------------------------------------------------------- |
| 完善本地历史记录体验             | 增加二次确认、搜索、按输入类型筛选、收藏重要问答等能力。                   |
| 增加材料清单引导式问答           | 根据用户是否首次办理、是否已有证件、目的地和出行目的生成更贴合的材料清单。 |
| 增加“我不知道怎么办”的选择题流程 | 将 Guidance 本地规则进一步产品化，用选择题帮助老人判断办理类型。           |
| 优化 RAG Prompt                  | 根据回归测试结果调整结构化 JSON 输出、风险提醒、材料字段和口吻。           |
| 增加知识库更新流程               | 建立资料采集、审核、导入、版本标记、回归测试和发布记录流程。               |
| 增加更多适老化设置               | 增加高对比度、简化模式、朗读速度、按钮大小、常用联系人等设置。             |
| 增加异常兜底和离线提示           | 对无网络、后端不可用、Dify 超时、ASR/TTS 失败提供更友好的兜底路径。        |
| 统一材料清单数据来源             | 决定使用前端本地 mock、后端静态接口或知识库生成，并保持字段一致。          |
| 强化 FAQ 与 RAG 分工             | FAQ 继续承担固定答案，RAG 承担个性化追问，减少重复调用。                   |

| 日志监控与运维后台 | 监控后端接口、RAG 命中率、ASR/TTS 失败率、响应时延和异常。       |

| 多端适配           | 根据需要扩展到 Web、小程序、平板、适老设备或政务服务终端。       |
| 人工服务协同       | 将当前 Toast 占位的客服、志愿者、家人协助升级为真实协同能力。    |

## 6. 上线前必须补充内容

上线前至少需要补充以下内容：

- 隐私政策：明确收集哪些数据、如何使用、如何保存、如何删除。
- 用户协议：明确服务边界、AI 回答限制、政策核实责任和使用规范。
- API Key 安全管理：禁止前端保存模型 Key，后端使用环境变量或密钥管理服务。
- 错误日志：建立后端错误日志、前端崩溃日志、ASR/TTS 失败日志和脱敏策略。
- 权限说明：说明麦克风、网络、存储或缓存等权限用途。
- 真实设备兼容测试：覆盖不同 Android 版本、屏幕尺寸、字体大小、系统语言和弱网环境。
- 政策来源审核：为知识库、FAQ、材料清单补充官方来源、更新时间和审核记录。
- 数据更新机制：明确政策资料、FAQ、口岸信息、养老服务数据如何更新和回滚。
- 外部服务可用性方案：处理 Dify、DashScope、Qwen 不可用或超时的兜底。
- 合规提示：政策类回答应提示以官方窗口或政府网站为准。

## 7. 项目交付还需要补充内容

如果作为公司级项目或正式商业交付，还需要补充：

- PRD 需求说明：明确目标用户、核心场景、需求优先级和非目标范围。
- 验收标准：定义每个功能模块的可验收行为和失败边界。
- 测试报告：包含单元测试、接口测试、真机测试、兼容性测试、无障碍测试和安全测试。
- 部署运维说明：说明后端部署、环境变量、服务依赖、日志目录、备份与恢复。
- 安全说明：包含鉴权、密钥、数据脱敏、权限、依赖漏洞和攻击面分析。
- 交接清单：列出代码仓库、环境配置、知识库、账号权限、部署信息和维护人。
- 版本发布流程：定义版本号、变更记录、灰度发布、回滚方案和发布验收。
- 监控与告警方案：覆盖接口延迟、错误率、RAG 命中率、外部服务失败率和资源使用率。
- 数据治理说明：定义资料来源审核、过期策略、冲突处理、数据分类和责任人。
- 运营后台说明：如后续提供知识库、FAQ、口岸、养老机构维护后台，需要补充操作手册。

## 8. 当前状态总结

当前项目已经完成适合课程或 Demo 展示的核心闭环：用户可以通过 Android 前端进行文字或语音提问，后端通过 Dify/RAG 和语音服务返回结果，前端可以展示结构化回答、朗读回答并保存本地历史。同时，首页 FAQ 静态详情、材料清单 mock、口岸信息和养老服务原型增强了场景完整度。

但当前项目尚未达到正式上线或公司级交付成熟度。后续重点应放在三类工作：第一，补齐政策来源、FAQ 内容、演示截图和 README；第二，统一 mock 与真实数据边界，完善材料、口岸、养老服务数据流程；第三，补充隐私、安全、测试、运维、监控和交付文档，确保项目从 Demo 能力逐步走向可维护、可审计、可上线的产品形态。
