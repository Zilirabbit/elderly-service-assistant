## 1. 项目开发目标

本项目拟开发一款面向老年用户的 Android 移动应用 Demo，围绕“政策查询、语音问答、表单预填、人工确认、材料草稿生成”形成完整办事辅助流程。开发阶段的核心目标不是建设完整政务系统，而是在有限周期内完成一个可运行、可展示、可解释的智能办事辅助原型。

开发成果应支持以下演示闭环：

1. 用户在 Android App 中通过文字或语音提出政策问题。
2. App 调用后端 FastAPI 服务。
3. 后端调用 Dify 应用 API。
4. Dify 基于政策知识库进行 RAG 检索，并调用 Qwen API 生成口语化回答。
5. App 展示政策解释、材料清单和下一步建议。
6. 用户进入表单填写流程。
7. 用户通过自然语言描述个人信息。
8. 后端调用 Dify Workflow 抽取结构化字段。
9. App 自动回填表单，并要求用户确认。
10. 用户或亲属确认后生成申请草稿结果。

## 2. 开发阶段总体原则

### 2.1 先跑通闭环，再完善细节

项目开发优先保证“能完整跑通”，不要过早追求多场景、多表单、多地区、多用户系统。第一版只支持一个高频办事场景和一套表单。

推荐优先场景：

- 长者津贴申请辅助
- 社区养老服务登记
- 长者医疗补贴申请辅助

### 2.2 先本地联调，再迁移云端

开发阶段采用本地优先策略：

```text
Android Studio
  ↓
本机 / 局域网 FastAPI
  ↓
本地虚拟机或本地 Docker Dify
  ↓
Qwen API
```

本地闭环稳定后，再迁移至腾讯云轻量应用服务器：

```text
Android App
  ↓
腾讯云服务器 FastAPI
  ↓
同机 Dify
  ↓
Qwen API
```

### 2.3 前端轻业务，后端控流程

Android App 主要负责交互展示，不直接调用 Dify、Qwen 或腾讯云 ASR。所有 API Key 均保存在后端环境变量或 Dify 配置中，避免打包进 APK。

### 2.4 AI 结果必须确认

所有 AI 生成的政策解释和表单字段均为辅助结果。表单字段必须经过本人或亲属确认后，才能进入草稿生成环节。

## 3. 开发环境准备

### 3.1 Android 开发环境

| 项目     | 说明                         |
| -------- | ---------------------------- |
| IDE      | Android Studio               |
| 语言     | Kotlin                       |
| UI       | Jetpack Compose              |
| 网络请求 | Retrofit + OkHttp            |
| 异步处理 | Kotlin Coroutines            |
| 语音录制 | MediaRecorder                |
| 语音播报 | Android TextToSpeech         |
| 测试设备 | Android 真机优先，模拟器备用 |

Android 端需要配置权限：

```xml
<uses-permission android:name="android.permission.INTERNET" />
<uses-permission android:name="android.permission.RECORD_AUDIO" />
```

如果开发阶段使用 HTTP 访问后端，需要在 `AndroidManifest.xml` 中允许明文请求：

```xml
<application
    android:usesCleartextTraffic="true">
</application>
```

### 3.2 后端开发环境

| 项目      | 说明                    |
| --------- | ----------------------- |
| 语言      | Python 3.11+            |
| 框架      | FastAPI                 |
| 服务运行  | Uvicorn                 |
| 数据校验  | Pydantic                |
| HTTP 调用 | httpx                   |
| 配置管理  | `.env`                  |
| API 调试  | Apifox / Postman / curl |
| 容器化    | Docker                  |

后端本地启动命令：

```bash
cd backend
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --reload --host 0.0.0.0 --port 8080
```

基础健康检查：

```bash
curl http://localhost:8080/health
```

期望返回：

```json
{ "status": "ok" }
```

### 3.3 Dify 开发环境

Dify 可先部署在本地虚拟机或本地 Docker 环境中。建议配置：

| 项目     | 建议                      |
| -------- | ------------------------- |
| 系统     | Ubuntu 22.04 / 24.04      |
| CPU      | 2 核最低，4 核更稳        |
| 内存     | 4GB 最低，8GB 更稳        |
| 磁盘     | 60GB 起步                 |
| 部署方式 | Docker Compose            |
| 模型     | Qwen API                  |
| 文档数量 | 第一版控制在 10-20 份以内 |

Dify 启动流程：

```bash
git clone https://github.com/langgenius/dify.git
cd dify/docker
cp .env.example .env
docker compose up -d
```

如服务器内存为 4GB，建议开启 swap 并降低 worker 数：

```bash
sudo fallocate -l 4G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
```

在 Dify `.env` 中可设置：

```env
SERVER_WORKER_AMOUNT=1
CELERY_WORKER_AMOUNT=1
EXPOSE_NGINX_PORT=8088
```

## 5. 开发阶段任务拆解

### 5.1 第一阶段：最小后端闭环

目标：确认 FastAPI 能调用 Dify，并返回政策回答。

任务：

- 创建 FastAPI 项目结构。
- 实现 `/health` 接口。
- 配置 Dify 政策问答应用。
- 在 Dify 中配置 Qwen 模型。
- 上传少量政策文档到知识库。
- 获取 Dify App API Key。
- 编写 FastAPI 调用 Dify 的服务类。
- 实现 `/api/v1/chat-policy` 接口。
- 使用 Apifox/Postman/curl 测试接口。

验收标准：

```text
输入：“我今年70岁，可以申请长者津贴吗？”
输出：系统返回口语化政策解释、申请条件、材料提示和下一步建议。
```

---

### 5.2 第二阶段：表单 Schema 与字段抽取

目标：支持自然语言转结构化表单字段。

任务：

- 设计一套表单 JSON Schema。
- 在后端实现 `/api/v1/forms/{formCode}`。
- 在 Dify 中创建字段抽取 Workflow。
- 设计字段抽取 Prompt。
- 要求 Dify Workflow 输出标准 JSON。
- 实现 `/api/v1/applications/{id}/extract-fields`。
- 对字段结果进行二次校验和状态标记。

字段状态建议：

| 状态         | 含义         |
| ------------ | ------------ |
| empty        | 未填写       |
| extracted    | AI 已抽取    |
| needs_review | 需要人工确认 |
| confirmed    | 已确认       |
| rejected     | 已驳回       |

验收标准：

```text
输入：“我叫陈大明，今年72岁，电话是91234567，住在九龙观塘。”
输出：姓名、年龄、电话、地址等字段被结构化抽取，并标记确认状态。
```

---

### 5.3 第三阶段：Android App 最小版本

目标：Android Studio 能跑通 App，并真实调用后端。

任务：

- 创建 Android Kotlin 项目。
- 配置 Retrofit + OkHttp。
- 编写 API Client。
- 创建首页、政策问答页、结果展示页。
- 实现文本输入政策查询。
- 调用 `/api/v1/chat-policy`。
- 展示政策回答和下一步建议。
- 增加 loading 和错误提示。

验收标准：

```text
在 Android Studio 中运行 App，用户输入政策问题后，App 能显示后端返回的政策回答。
```

---

### 5.4 第四阶段：表单预填与确认页面

目标：Android App 支持动态表单展示和字段确认。

任务：

- App 调用 `/api/v1/forms/{formCode}` 获取表单 Schema。
- 动态渲染表单字段。
- 用户输入自然语言信息。
- App 调用字段抽取接口。
- 将抽取结果自动回填表单。
- 对低置信度字段显示“请确认”。
- 添加本人确认页面。
- 添加亲属确认页面或模拟确认页。
- 生成申请草稿结果页。

验收标准：

```text
用户输入个人信息后，App 自动回填表单，并进入确认流程。
```

---

### 5.5 第五阶段：语音输入与语音播报

目标：增强适老化交互体验。

任务：

- Android 端加入录音按钮。
- 实现语音文件上传接口。
- 后端接入腾讯云 ASR。
- 返回识别文本。
- 将识别文本用于政策问答或字段抽取。
- Android 端加入 TTS 播报。
- 增加文字输入 fallback。

验收标准：

```text
用户点击语音按钮说话，App 能识别为文字并继续完成问答或填表。
```

注意：比赛现场语音容易受噪声影响，因此必须保留文字输入备用方案。

---

### 5.6 第六阶段：云端部署与最终联调

目标：将 Dify 和 FastAPI 部署到腾讯云轻量应用服务器，完成公网访问。

任务：

- 购买或准备腾讯云轻量应用服务器。
- 安装 Docker 和 Docker Compose。
- 部署 Dify。
- 配置 Qwen API。
- 上传政策文档。
- 创建 Dify 政策问答 App 和字段抽取 Workflow。
- 部署 FastAPI 后端。
- 配置 `.env`。
- 放通服务器端口。
- Android App 修改 `BASE_URL` 为服务器公网 IP。
- 进行真机联调。

推荐端口：

| 服务    | 端口 |
| ------- | ---: |
| FastAPI | 8080 |
| Dify    | 8088 |
| SSH     |   22 |

验收标准：

```text
Android App 通过公网 IP 调用云端 FastAPI，并完成政策问答、字段抽取和表单确认流程。
```

````
## 12. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| Dify 部署内存不足 | 服务卡顿或容器重启 | 开 swap，降低 worker，减少文档，必要时升级服务器 |
| 政策回答不准确 | 影响可信度 | 强制基于知识库回答，资料不足时提示人工咨询 |
| 语音识别不稳定 | 影响现场展示 | 保留文字输入 fallback |
| Android 访问后端失败 | App 无法演示 | 提前测试公网 IP，准备本地备用和录屏 |
| Qwen API 超时 | 回答延迟 | 设置超时时间和错误提示 |
| 字段抽取格式不稳定 | 表单无法回填 | Dify Workflow 输出 JSON，后端二次校验 |
| 比赛网络不稳定 | 演示失败 | 云端部署 + 本地备用 + 录屏备用 |
| API Key 泄露 | 安全风险 | Key 只放后端和 Dify，不放 Android |

## 13. 比赛演示脚本

### 13.1 标准演示流程

1. 打开 Android App。
2. 点击“我要咨询政策”。
3. 输入或语音说：“我今年70岁，可以申请长者津贴吗？”
4. App 显示政策解释、申请条件和材料清单。
5. 点击“帮我填写申请表”。
6. 输入或语音说：“我叫陈大明，今年72岁，电话是91234567，住在九龙观塘。”
7. App 自动回填姓名、年龄、电话和地址。
8. 展示需要确认的字段。
9. 点击“本人确认”。
10. 进入亲属确认页。
11. 点击“亲属已确认”。
12. 展示申请草稿结果。

```text
直接切换为文字输入。
````

```text
使用本地局域网后端或播放提前录制的视频。
```

```text
使用预设问题，减少模型等待时间。
```

## 15. 开发阶段总结表述

本项目开发阶段采用“先本地闭环、后云端部署”的实施路径。首先在本地环境完成 Dify、Qwen、FastAPI 与 Android App 的核心链路验证，确保政策问答和表单预填流程可运行；随后将后端服务和 Dify 迁移至腾讯云轻量应用服务器，通过公网 IP 为 Android App 提供稳定访问接口。开发过程中，系统以一个高频政务场景为核心，优先完成“政策问答—表单预填—人工确认—草稿生成”的最小可用闭环，并在此基础上逐步加入语音识别、语音播报和适老化交互设计。

在工程实现上，Android App 负责用户交互和适老化展示，FastAPI 作为后端网关统一封装 Dify 应用 API、腾讯云 ASR 和表单状态管理，Dify 负责政策知识库检索与 Qwen 模型调用。该开发路径既降低了自建 RAG 的复杂度，又保证了业务流程、数据状态和安全边界的可控性，适合在比赛周期内快速完成可演示原型。
