## 1. 项目开发目标

本项目拟开发一款面向老年用户的 Android 移动应用 Demo，围绕“政策查询、语音问答、表单预填、人工确认、材料草稿生成”形成完整办事辅助流程。开发阶段的核心目标不是建设完整政务系统，而是在有限周期内完成一个可运行、可展示、可解释的智能办事辅助原型。

开发成果应支持以下演示闭环：

1. 用户在 Android App 中通过文字或语音提出政策问题。
2. App 调用后端 FastAPI 服务。
3. 后端调用 Dify 应用 API。
4. Dify 基于政策知识库进行 RAG 检索，并调用 Qwen API 生成口语化回答。
5. App 展示政策解释、材料清单和下一步建议。
6. 用户进入表单填写流程。
7. 用户通过自然语言描述个人信息。
8. 后端调用 Dify Workflow 抽取结构化字段。
9. App 自动回填表单，并要求用户确认。
10. 用户或亲属确认后生成申请草稿结果。

## 2. 开发阶段总体原则

### 2.1 先跑通闭环，再完善细节

项目开发优先保证“能完整跑通”，不要过早追求多场景、多表单、多地区、多用户系统。第一版只支持一个高频办事场景和一套表单。

推荐优先场景：

- 长者津贴申请辅助
- 社区养老服务登记
- 长者医疗补贴申请辅助

### 2.2 先本地联调，再迁移云端

开发阶段采用本地优先策略：

```text
Android Studio
  ↓
本机 / 局域网 FastAPI
  ↓
本地虚拟机或本地 Docker Dify
  ↓
Qwen API
```

本地闭环稳定后，再迁移至腾讯云轻量应用服务器：

```text
Android App
  ↓
腾讯云服务器 FastAPI
  ↓
同机 Dify
  ↓
Qwen API
```

### 2.3 前端轻业务，后端控流程

Android App 主要负责交互展示，不直接调用 Dify、DashScope/Qwen、ASR/TTS 模型。所有 API Key 均保存在后端环境变量或 Dify 配置中，避免打包进 APK。

### 2.4 AI 结果必须确认

所有 AI 生成的政策解释和表单字段均为辅助结果。表单字段必须经过本人或亲属确认后，才能进入草稿生成环节。

```bash

sudo mkswap /swapfile
sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
```

在 Dify `.env` 中可设置：

```env
SERVER_WORKER_AMOUNT=1
CELERY_WORKER_AMOUNT=1
EXPOSE_NGINX_PORT=8088
```

## 5. 开发阶段任务拆解

### 5.1 第一阶段：最小后端闭环

目标：确认 FastAPI 能调用 Dify，并返回政策回答。

任务：

- 创建 FastAPI 项目结构。
- 实现 `/health` 接口。
- 配置 Dify 政策问答应用。
- 在 Dify 中配置 Qwen 模型。
- 上传少量政策文档到知识库。
- 获取 Dify App API Key。
- 编写 FastAPI 调用 Dify 的服务类。
- 实现 `/api/v1/chat-policy` 接口。
- 使用 Apifox/Postman/curl 测试接口。

验收标准：

```text
输入：“我今年70岁，可以申请长者津贴吗？”
输出：系统返回口语化政策解释、申请条件、材料提示和下一步建议。
```

---

### 5.2 第二阶段：表单 Schema 与字段抽取

目标：支持自然语言转结构化表单字段。

任务：

- 设计一套表单 JSON Schema。
- 在后端实现 `/api/v1/forms/{formCode}`。
- 在 Dify 中创建字段抽取 Workflow。
- 设计字段抽取 Prompt。
- 要求 Dify Workflow 输出标准 JSON。
- 实现 `/api/v1/applications/{id}/extract-fields`。
- 对字段结果进行二次校验和状态标记。

字段状态建议：

| 状态         | 含义         |
| ------------ | ------------ |
| empty        | 未填写       |
| extracted    | AI 已抽取    |
| needs_review | 需要人工确认 |
| confirmed    | 已确认       |
| rejected     | 已驳回       |

验收标准：

```text
输入：“我叫陈大明，今年72岁，电话是91234567，住在九龙观塘。”
输出：姓名、年龄、电话、地址等字段被结构化抽取，并标记确认状态。
```

### 5.5 第五阶段：语音输入、查询改写与语音播报

目标：增强适老化交互体验，并解决普通话、粤语、方言输入对 RAG 检索稳定性的影响。本阶段不直接将 ASR 识别文本送入知识库检索，而是在后端增加“查询改写”步骤，将用户口语、粤语、方言、错别字表达统一改写为标准简体中文检索问题，再调用 Dify/RAG。

核心原则：

- 本项目 5.5 阶段统一使用阿里云百炼 / DashScope API Key 作为 Qwen、ASR、云端 TTS 的模型鉴权入口。
- 一个 DashScope API Key 不等于所有模型都自动可用，也不等于所有模型都使用同一种调用方式；不同模型仍需分别配置模型名、endpoint、协议、参数和权限。
- ASR 只负责把语音变成原始文字 `originalText`。
- RAG 前必须执行查询改写，将 `originalText` 改写为标准普通话检索问题 `searchQuery`。
- RAG 后固定返回简体中文普通话展示文本 `displayText`。
- 语音播报不直接朗读完整展示文本，而是单独生成更适合听的 `ttsText`。
- Android 只播放后端返回的 `audioUrl`；如果没有 `audioUrl`，提示“朗读服务暂时不可用”，不再使用 Android 本地 `TextToSpeech` 兜底。

第一版模型选择：

| 用途 | 推荐模型/方案 |
|---|---|
| 查询改写 | 阿里云百炼 `qwen-plus` |
| ttsText 改写 | 阿里云百炼 `qwen-plus` |
| 语音识别 | 阿里云百炼 `qwen3-asr-flash` |
| 方言/多语种识别备用 | 阿里云百炼 `fun-asr` |
| 语音播报 | 阿里云百炼 / DashScope `cosyvoice-v3-flash` |
| 播放控制 | Android `MediaPlayer` 播放后端缓存音频 |

API Key 与权限要求：

- 后端统一通过 `DASHSCOPE_API_KEY` 调用阿里云百炼 / DashScope。
- API Key 建议选择“全部”权限，并确认业务空间、地域、模型权限、免费额度或按量付费状态可用。
- Android 不保存 `DASHSCOPE_API_KEY`，不直接调用 Qwen、ASR 或 TTS。
- Dify 仍保留自己的 App API Key，负责 RAG 应用调用。

任务：

- Android 问答输入区加入麦克风按钮，点击后弹出底部语音输入面板。
- 语音输入面板参考即时通讯类输入体验，包含“点击说话 / 正在听您说话 / 正在识别 / 没听清，点击说话”等状态。
- 增加语种选择入口，第一版支持普通话、方言免切换、英语。
- Android 端申请 `RECORD_AUDIO` 权限，使用 `MediaRecorder` 录制音频。
- 实现语音文件上传接口：

```http
POST /api/v1/asr/transcribe
```

- 后端通过阿里云百炼 / DashScope ASR 服务返回原始识别文本 `originalText`，第一版优先使用 `qwen3-asr-flash`，必要时以 `fun-asr` 作为备用。
- Android 将识别文本展示给用户确认：

```text
我听到的是：……
[正确，继续] [重新说一遍] [手动修改]
```

- 用户确认后，Android 调用政策问答接口：

```http
POST /api/v1/chat-policy
```

- 后端在调用 Dify/RAG 前，先执行查询改写：

```text
originalText → searchQuery
```

示例：

```text
用户原话：我张证快过期啦，想再去香港，要点搞？
检索问题：往来港澳通行证即将过期，如何办理换证或续签？需要哪些材料？
```

- Dify 使用 `searchQuery` 检索知识库，并生成普通话简体中文展示文本 `displayText`。
- 后端再根据 `displayText` 生成适合朗读的 `ttsText`。
- 若用户选择普通话播报，则生成普通话 `ttsText`。
- 若用户选择粤语播报，则将 `displayText` 转换为轻度粤语口语化播报文本，并使用支持粤语音色的阿里云百炼 / DashScope TTS。
- 后端实现 TTS 服务生成音频文件和缓存能力，第一版即启用云端 TTS。
- Android 播放后端返回的 `audioUrl`。
- 若后端未返回音频，则 Android 提示“朗读服务暂时不可用，请稍后再试”，不使用本地 TTS fallback。
- 静态内容如操作指南、首页提示、按钮说明、材料清单说明，也通过后端 TTS 接口生成并缓存到服务器静态目录，避免重复调用 TTS。
- 动态问答内容采用实时 TTS + 缓存策略，缓存 key 使用：

```text
hash(ttsText + language + voice + speed)
```

建议交互流程：

```text
点击麦克风
→ 弹出底部语音面板
→ 用户选择普通话 / 方言免切换 / 英语
→ App 录音
→ 上传 FastAPI 后端
→ 后端调用 ASR
→ 返回 originalText
→ 用户确认或修改
→ 后端执行 query rewrite，得到 searchQuery
→ Dify/RAG 检索
→ 返回 displayText
→ 生成 ttsText
→ TTS 生成或命中缓存 audioUrl
→ App 展示 displayText，并播放 audioUrl
```

## 12. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| Dify 部署内存不足 | 服务卡顿或容器重启 | 开 swap，降低 worker，减少文档，必要时升级服务器 |
| 政策回答不准确 | 影响可信度 | 强制基于知识库回答，资料不足时提示人工咨询 |
| 语音识别不稳定 | 影响现场展示 | 保留文字输入 fallback |
| Android 访问后端失败 | App 无法演示 | 提前测试公网 IP，准备本地备用和录屏 |
| Qwen API 超时 | 回答延迟 | 设置超时时间和错误提示 |
| 字段抽取格式不稳定 | 表单无法回填 | Dify Workflow 输出 JSON，后端二次校验 |
| 比赛网络不稳定 | 演示失败 | 云端部署 + 本地备用 + 录屏备用 |
| API Key 泄露 | 安全风险 | Key 只放后端和 Dify，不放 Android |

## 15. 开发阶段总结表述

本项目开发阶段采用“先本地闭环、后云端部署”的实施路径。首先在本地环境完成 Dify、Qwen、FastAPI 与 Android App 的核心链路验证，确保政策问答和表单预填流程可运行；随后将后端服务和 Dify 迁移至腾讯云轻量应用服务器，通过公网 IP 为 Android App 提供稳定访问接口。开发过程中，系统以一个高频政务场景为核心，优先完成“政策问答—表单预填—人工确认—草稿生成”的最小可用闭环，并在此基础上逐步加入语音识别、语音播报和适老化交互设计。

在工程实现上，Android App 负责用户交互和适老化展示，FastAPI 作为后端网关统一封装 Dify 应用 API、阿里云百炼 / DashScope ASR、Qwen 文本模型、云端 TTS 和表单状态管理，Dify 负责政策知识库检索与问答应用编排。该开发路径既降低了自建 RAG 的复杂度，又保证了业务流程、数据状态和安全边界的可控性，适合在比赛周期内快速完成可演示原型。
