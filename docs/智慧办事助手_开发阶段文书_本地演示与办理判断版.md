## 1. 项目开发目标

本项目拟开发一款面向中老年用户的 Android 移动应用 Demo，围绕“政策问答、办理情况判断、材料清单、窗口沟通话术、语音输入与语音播报”形成完整办事辅助流程。开发阶段的核心目标不是建设完整政务系统，也不是替代线下窗口填表，而是在有限周期内完成一个可运行、可展示、可解释的智能办事辅助原型。

当前阶段将“AI 表单预填”弱化为“办事信息预整理”。原因是港澳通行证首次办理、换证等场景仍需本人到线下窗口办理，线下大厅通常也有工作人员协助。因此系统的核心价值应放在：

1. 帮助老人判断自己属于首次办证、换证、再次签注还是非旅游类签注。
2. 帮助老人提前知道去哪办、带什么、是否可尝试自助机。
3. 帮助老人生成给窗口工作人员看的简短说明。
4. 通过标准化问题提升 RAG 检索命中率，避免老人不知道如何提问。

开发成果应支持以下演示闭环：

1. 用户进入 Android App 首页。
2. 用户可以选择“直接提问”，进入已有政策问答页。
3. 用户也可以点击“我不知道自己该怎么办”，进入办理情况判断流程。
4. 系统通过单页滑动“办理情况问卷”收集 5 个关键信息：是否已有港澳通行证、证件是否有效、办理事项、目的地、出行目的。
5. 前端或后端根据固定规则初步判断用户属于哪类办理情形。
6. 系统把结构化判断结果拼成标准化 RAG 查询问题。
7. App 调用 FastAPI 后端，后端调用 Dify/RAG 知识库生成回答。
8. App 展示办理类型、推荐方式、材料清单、注意事项和窗口话术。
9. 用户可以通过文字或语音继续追问。
10. 系统支持语音识别、查询改写、普通话/粤语播报和音频缓存。

第一版重点围绕港澳通行证与签注办理场景，不再把完整政务表单在线预填作为核心验收项。表单草稿、亲属确认、导出申请草稿可保留为后续增强功能。

## 2. 开发阶段总体原则

### 2.1 先跑通本地闭环，再完善细节

项目开发优先保证“能完整跑通”，不要过早追求多场景、多表单、多地区、多用户系统。当前第一版聚焦一个高频场景：

```text
港澳通行证 / 签注办理辅助
```

该场景下优先完成：

- 直接政策问答
- “不知道自己该怎么办”引导流程
- 材料清单
- 自助机 / 窗口办理建议
- 给工作人员看的说明
- 语音输入与语音播报

暂缓或弱化：

- 完整线上表单预填
- 真实在线政务提交
- 多用户账号系统
- 云端公网部署
- 复杂亲属协同审批

### 2.2 本地 / 局域网优先，云端部署暂缓

当前阶段不再把腾讯云轻量服务器、公网 IP、Nginx、域名、HTTPS 作为主线任务。开发与比赛演示优先采用：

```text
Android Studio / Android 真机
  ↓
本机或局域网 FastAPI
  ↓
本地虚拟机 / 本地 Docker Dify
  ↓
Qwen / DashScope API
```

说明：

- Android 真机与电脑处于同一 Wi-Fi 时，可通过电脑局域网 IP 调用本地 FastAPI。
- Dify 可以部署在本地虚拟机或本地 Docker。
- Qwen、ASR、TTS 仍通过阿里云百炼 / DashScope API 调用，因此需要保留网络访问能力。
- 云端部署仅作为后续扩展，不作为当前开发阶段的必做验收项。

### 2.3 前端轻业务，但可保留简单规则

Android App 主要负责交互展示，不直接保存 Dify、DashScope/Qwen、ASR/TTS 的 API Key。所有模型调用仍由 FastAPI 或 Dify 统一封装。

但“办理情况判断”的第一版可以在前端保留简单固定规则，因为它本质上是问卷选项状态判断，不涉及敏感密钥，也方便离线演示和快速调试。后续如规则变复杂，再考虑迁移到后端服务。

### 2.4 AI 回答必须提示人工核实

所有 AI 生成的政策解释、材料清单和办理建议均为辅助结果。涉及证件办理、签注类型、材料要求和窗口规则时，页面应提示：

```text
以上结果为办事辅助建议，具体要求以当地出入境管理部门或现场窗口为准。
```

### 2.5 不替代窗口，只降低白跑和问错成本

项目不宣称“线上代办”或“AI 自动提交表单”。当前阶段的合理定位是：

```text
AI 办事分诊 + 材料预检查 + 窗口话术辅助
```

这比单纯“表单预填”更贴合线下办理实际，也更容易在比赛答辩中解释其必要性。

<application

### 3.3 Dify 开发环境

Dify 可先部署在本地虚拟机或本地 Docker 环境中。建议配置：

| 项目     | 建议                      |
| -------- | ------------------------- |
| 系统     | Ubuntu 22.04 / 24.04      |
| CPU      | 2 核最低，4 核更稳        |
| 内存     | 4GB 最低，8GB 更稳        |
| 磁盘     | 60GB 起步                 |
| 部署方式 | Docker Compose            |
| 模型     | Qwen API                  |
| 文档数量 | 第一版控制在 10-20 份以内 |

Dify 启动流程：

```bash
git clone https://github.com/langgenius/dify.git
cd dify/docker
cp .env.example .env
docker compose up -d
```

如本地虚拟机内存为 4GB，建议开启 swap 并降低 worker 数：

```bash
sudo fallocate -l 4G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
```

在 Dify `.env` 中可设置：

```env
SERVER_WORKER_AMOUNT=1
CELERY_WORKER_AMOUNT=1
EXPOSE_NGINX_PORT=8088
```

### 5.2 第二阶段：办理判断规则与演示路径准备

目标：把“AI 表单预填”从当前主线中移出，改为准备可稳定演示的办理判断规则、固定问卷路径和标准化 RAG 提问模板。当前版本不承诺自动识别姓名、地址、证件号，也不把语音表单预填作为验收项。

任务：

- 确定 5 个办理判断字段：是否已有港澳通行证、证件是否有效、办理事项、目的地、出行目的。
- 设计 3 条固定演示路径：首次办理、证件过期换证、签注过期再次办理。
- 为每条路径准备 `caseType`、`standardQuestion`、`windowScript` 和 `recommendedAction`。
- 明确第一版规则放在 Android 前端状态逻辑中，不新增后端 guidance 接口。
- 准备人工核实提醒文案，避免把辅助判断说成正式办理结论。

Android 内部数据建议：

```kotlin
data class GuidanceProfile(
    val hasPass: String,
    val passValid: String,
    val applyType: String,
    val destination: String,
    val purpose: String,
)

data class GuidanceResult(
    val caseType: String,
    val standardQuestion: String,
    val windowScript: String,
    val recommendedAction: String,
)
```

验收标准：

```text
文档和演示路径中不再把表单预填列为核心功能。用户通过问卷中的 5 个问题即可得到办理类型、标准化问题、窗口说明和下一步建议。
```

### 5.4 第四阶段：办理情况判断与标准化 RAG 提问

目标：在已有问答页前增加“我不知道自己该怎么办”入口，通过单页滑动问卷帮助中老年用户判断办理类型，并把判断结果转成高质量 RAG 查询问题。该阶段不以完整表单在线预填为核心，而是以“少白跑、少问错、到窗口能说清”为目标。

页面入口：

```text
服务页 / 首页
  ↓
港澳通行证 / 签注办理
  ↓
[我想直接提问]      → 进入已有问答页
[我不知道自己该怎么办] → 进入办理情况问卷页
```

需要收集的 5 个字段：

```json
{
  "hasPass": "有 / 没有 / 不清楚",
  "passValid": "在有效期内 / 已经过期 / 不知道怎么看",
  "applyType": "第一次办理 / 签注过期或用完 / 通行证过期 / 通行证丢了或坏了 / 不确定",
  "destination": "香港 / 澳门 / 香港和澳门都去 / 还没确定",
  "purpose": "旅游 / 探亲 / 商务 / 学习工作逗留 / 不确定"
}
```

问卷展示建议：

1. 您现在有没有港澳通行证？
2. 您的港澳通行证还在有效期内吗？
3. 您这次想办理什么？
4. 您想去哪里？
5. 您去港澳的目的是什么？

页面形态建议：

```text
办理情况问卷                         [朗读全部]

请回答下面 5 个问题，我们帮您判断该怎么办。

1. 您现在有没有港澳通行证？              [朗读]
[我有] [我没有] [不清楚]

2. 您的港澳通行证还在有效期内吗？        [朗读]
[在有效期内] [已经过期] [不知道怎么看]

3. 您这次想办理什么？                    [朗读]
[第一次办理] [签注过期或用完] [通行证过期] [丢了或坏了] [不确定]

……

[生成办理建议]
```

交互规则：

- 5 个问题放在同一个纵向滑动页面，不做分页。
- 每个问题是一张卡片，题目右侧放小喇叭按钮，用于朗读该问题。
- 顶部提供“朗读全部”，依次播报问卷说明和 5 个问题。
- 选项使用大号胶囊按钮或卡片按钮，不使用小号单选圆点。
- 选中后高亮，允许用户改选。
- 底部固定或清晰展示“生成办理建议”按钮。
- 如果未答完，提示“还有 X 个问题没选”，并滚动或定位到未答题卡片。

固定规则第一版：

| 条件 | 初步判断 | 下一步 |
|---|---|---|
| `hasPass = 没有` | 首次办理往来港澳通行证及签注 | 提示本人到窗口办理 |
| `passValid = 已经过期` | 换发港澳通行证 | 提示按换证流程办理 |
| `applyType = 通行证丢了或坏了` | 补发 / 换发港澳通行证 | 提示窗口办理 |
| `passValid = 在有效期内` 且 `applyType = 签注过期或用完` 且 `purpose = 旅游` | 再次办理旅游签注 | 优先提示自助签注机或线上申请后打印签注 |
| `purpose = 探亲 / 商务 / 学习工作逗留` | 非旅游类签注 | 提示可能需要额外材料，建议窗口咨询 |
| 任一关键字段为 `不清楚 / 不确定` | 信息不足 | 给出查看证件方法，并建议人工窗口确认 |

标准化 RAG 查询示例：

```text
用户已有有效港澳通行证，但香港旅游签注已经过期或用完。请根据官方资料说明：是否可以通过自助签注机办理、需要携带什么材料、哪些情况需要去窗口、到现场应该怎么和工作人员说明。
```

结果页建议展示：

```text

推荐办理方式：
优先尝试自助签注机或线上平台申请后打印签注。

建议携带：

给工作人员看的说明：

```

### 5.5 第五阶段：语音输入、查询改写与语音播报

目标：增强适老化交互体验，并解决普通话、粤语、方言输入对 RAG 检索稳定性的影响。本阶段不直接将 ASR 识别文本送入知识库检索，而是在后端增加“查询改写”步骤，将用户口语、粤语、方言、错别字表达统一改写为标准简体中文检索问题，再调用 Dify/RAG。

核心原则：

- 本项目 5.5 阶段统一使用阿里云百炼 / DashScope API Key 作为 Qwen、ASR、云端 TTS 的模型鉴权入口。
- 一个 DashScope API Key 不等于所有模型都自动可用，也不等于所有模型都使用同一种调用方式；不同模型仍需分别配置模型名、endpoint、协议、参数和权限。
- ASR 只负责把语音变成原始文字 `originalText`。
- RAG 前必须执行查询改写，将 `originalText` 改写为标准普通话检索问题 `searchQuery`。
- RAG 后固定返回简体中文普通话展示文本 `displayText`。
- 语音播报不直接朗读完整展示文本，而是单独生成更适合听的 `ttsText`。
- Android 只播放后端返回的 `audioUrl`；如果没有 `audioUrl`，提示“朗读服务暂时不可用”，不再使用 Android 本地 `TextToSpeech` 兜底。

第一版模型选择：

| 用途 | 推荐模型/方案 |
|---|---|
| 查询改写 | 阿里云百炼 `qwen-plus` |
| ttsText 改写 | 阿里云百炼 `qwen-plus` |
| 语音识别 | 阿里云百炼 `qwen3-asr-flash` |
| 方言/多语种识别备用 | 阿里云百炼 `fun-asr` |
| 语音播报 | 阿里云百炼 / DashScope `cosyvoice-v3-flash` |
| 播放控制 | Android `MediaPlayer` 播放后端缓存音频 |

API Key 与权限要求：

- 后端统一通过 `DASHSCOPE_API_KEY` 调用阿里云百炼 / DashScope。
- API Key 建议选择“全部”权限，并确认业务空间、地域、模型权限、免费额度或按量付费状态可用。
- Android 不保存 `DASHSCOPE_API_KEY`，不直接调用 Qwen、ASR 或 TTS。
- Dify 仍保留自己的 App API Key，负责 RAG 应用调用。

任务：

- Android 问答输入区加入麦克风按钮，点击后弹出底部语音输入面板。
- 语音输入面板参考即时通讯类输入体验，包含“点击说话 / 正在听您说话 / 正在识别 / 没听清，点击说话”等状态。
- 增加语种选择入口，第一版支持普通话、方言免切换、英语。
- Android 端申请 `RECORD_AUDIO` 权限，使用 `MediaRecorder` 录制音频。
- 实现语音文件上传接口：

```http
POST /api/v1/asr/transcribe
```

- 后端通过阿里云百炼 / DashScope ASR 服务返回原始识别文本 `originalText`，第一版优先使用 `qwen3-asr-flash`，必要时以 `fun-asr` 作为备用。
- Android 将识别文本展示给用户确认：

```text
我听到的是：……
[正确，继续] [重新说一遍] [手动修改]
```

- 用户确认后，Android 调用政策问答接口：

```http
POST /api/v1/chat-policy
```

- 后端在调用 Dify/RAG 前，先执行查询改写：

```text
originalText → searchQuery
```

示例：

```text
用户原话：我张证快过期啦，想再去香港，要点搞？
检索问题：往来港澳通行证即将过期，如何办理换证或续签？需要哪些材料？
```

- Dify 使用 `searchQuery` 检索知识库，并生成普通话简体中文展示文本 `displayText`。
- 后端再根据 `displayText` 生成适合朗读的 `ttsText`。
- 若用户选择普通话播报，则生成普通话 `ttsText`。
- 若用户选择粤语播报，则将 `displayText` 转换为轻度粤语口语化播报文本，并使用支持粤语音色的阿里云百炼 / DashScope TTS。
- 后端实现 TTS 服务生成音频文件和缓存能力，第一版即启用云端 TTS。
- Android 播放后端返回的 `audioUrl`。
- 若后端未返回音频，则 Android 提示“朗读服务暂时不可用，请稍后再试”，不使用本地 TTS fallback。
- 静态内容如操作指南、首页提示、按钮说明、材料清单说明，也通过后端 TTS 接口生成并缓存到服务器静态目录，避免重复调用 TTS。
- 动态问答内容采用实时 TTS + 缓存策略，缓存 key 使用：

```text
hash(ttsText + language + voice + speed)
```

建议交互流程：

```text
点击麦克风
→ 弹出底部语音面板
→ 用户选择普通话 / 方言免切换 / 英语
→ App 录音
→ 上传 FastAPI 后端
→ 后端调用 ASR
→ 返回 originalText
→ 用户确认或修改
→ 后端执行 query rewrite，得到 searchQuery
→ Dify/RAG 检索
→ 返回 displayText
→ 生成 ttsText
→ TTS 生成或命中缓存 audioUrl
→ App 展示 displayText，并播放 audioUrl
```

## 12. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| Dify 本地部署内存不足 | 服务卡顿或容器重启 | 开 swap，降低 worker，减少文档，必要时只保留核心知识库 |
| 政策回答不准确 | 影响可信度 | 强制基于知识库回答，资料不足时提示人工咨询 |
| 老人不知道如何提问 | 自由问答入口使用困难 | 增加“我不知道自己该怎么办”问卷引导 |
| 问卷判断过度简化 | 可能无法覆盖所有真实情况 | 显示“可能属于”，并提醒以窗口为准 |
| 语音识别不稳定 | 影响现场展示 | 保留文字输入 fallback，准备固定演示语音或录屏 |
| TTS 生成失败 | 不能朗读 | 保留文字答案，提示朗读服务暂时不可用 |
| 手机无法访问本机后端 | App 无法联调 | 确认同一 Wi-Fi、局域网 IP、防火墙和 8080 端口 |
| Qwen / DashScope API 超时 | 回答或语音链路变慢 | 设置超时时间和错误提示，准备预设问题和录屏 |
| 比赛网络不稳定 | API 调用失败 | 保留文字演示路径、本地截图、录屏备用 |
| API Key 泄露 | 安全风险 | Key 只放后端和 Dify，不放 Android |
| 被质疑不上云 | 架构完整性受质疑 | 答辩说明当前阶段聚焦可运行原型，云端部署是后续扩展，不影响核心功能验证 |

## 15. 开发阶段总结表述

本项目开发阶段采用“本地闭环优先、云端部署暂缓”的实施路径。当前版本不以建设完整政务系统或实现线上代办为目标，而是聚焦中老年用户在港澳通行证与签注办理前最常见的问题：不知道自己属于哪种情况、不知道是否能自助机办理、不知道要带什么材料、到窗口不知道怎么说明。系统通过“直接问答 + 办理情况问卷”双入口，既保留自由提问能力，也为不会组织问题的老人提供滑动问卷式引导。

在功能链路上，Android App 负责适老化交互展示，包括大按钮、语音输入、语音播报、常见问题快捷入口和“我不知道自己该怎么办”办理情况问卷。问卷采用单页纵向滑动，每题卡片支持题目朗读，底部统一生成办理建议。FastAPI 作为本地后端网关，统一封装 Dify/RAG、Qwen 查询改写、DashScope ASR/TTS 和音频缓存。Dify 负责政策知识库检索与问答生成。办理情况判断阶段通过固定规则收集用户是否已有港澳通行证、证件是否有效、签注状态、目的地和出行目的等关键信息，再将结构化结果转换为标准化 RAG 查询问题，从而提升检索准确性和回答稳定性。

与早期方案相比，当前文书已将“AI 表单预填”弱化为“办事信息预整理”，将核心卖点调整为“AI 办事分诊、材料预检查和窗口话术辅助”。这样更符合港澳通行证首次办理、换证等线下窗口办理场景，也避免夸大线上提交能力。云端部署相关任务已从主线中缩减，比赛 Demo 以本机 FastAPI、本地虚拟机或 Docker Dify、Android 局域网访问为主要演示方式。若后续时间和预算允许，再将 FastAPI 与 Dify 迁移至云服务器作为扩展能力。
